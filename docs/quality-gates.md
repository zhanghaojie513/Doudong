# 完成定义与质量门

> **这份文档的作用**：定义"一片工作算不算做完"。它把 [goal.md](goal.md) 的四条性质
> 翻译成每一片交付都必须通过的门槛。
> **它不是什么**：不是测试清单（测试是手段），不是排期（见 [plan.md](plan.md)）。
>
> **核心原则**：门的数量少而有约束力。宁可六道门都过硬，不要二十道门都被绕过。

---

## 一、为什么需要这份文档

M1 结束了 15 个真实缺陷之后，最有价值的一条教训是：

> **能力被实现了、被测试了、被勾选了——但它没有接在生产路径上。**

`IContextCompactor` 有 9 项自检全绿，`status.md` 也写了"已实现"，
但 `LoopAgentRuntime` 根本没有压缩器参数。测试测的是算法，
没人检查这个算法有没有被调用。

同类问题在 M1 出现过至少三次：

| 现象 | 本来应该被哪道门拦住 |
|---|---|
| 压缩能力只在测试里 | 门 3：生产路径可达性 |
| 审批决定枚举值使用点为 0 | 门 4：能力有真实使用点 |
| usage 走自定义附加属性，框架看不见 | 门 2：外部契约对齐 |

**所以门的作用不是"多测一遍"，而是"验证这件事真的发生了"。**

---

## 二、六道门

每一片交付（一个功能、一次修复、一个里程碑项）都必须过全部六道门。
不适用的门要明确写"为何不适用"，不能默认跳过。

### 门 1：失败证据先于修复

**要求**：改动之前存在一个能失败的探针（测试、脚本或手工复现步骤）。
修复之后，同一个探针通过。

**为什么**：没有失败证据的修复，无法证明它修的是真实存在的问题。
更糟的是，它可能是"改了一个本不存在的 bug"，同时引入新问题。

**反例**：
- "我加了压缩器参数" —— 但没有先证明过长历史真的会失败
- 修 CI 时先改 workflow 参数，没有本地复现（结果改错了地方）

**例外**：纯文档改动、纯重命名、添加注释。

### 门 2：外部契约对齐

**要求**：与外部系统（provider 协议、SDK 类型、平台行为）交互时，行为对照**真实行为**
验证过，不能只按文档或直觉实现。

**为什么**：M1 的四个协议缺陷全部来自"我以为它是这样"：
- `finish_reason` 被从 `delta` 读，实际是 `choices[0]` 的兄弟字段
- `ProcessStartInfo.Environment` 初始装着父进程全部变量，不是空的
- `AsyncLocal` 不能从 `Task.Run` 内部传出
- `UsageContent` 是框架识别的类型，自定义附加属性不是

**做法**：写一个小探针直接观察外部行为，把结论写进注释。探针可以丢弃，
结论必须留下。

### 门 3：生产路径可达

**要求**：新能力必须能从**用户实际使用的入口**触达。测试通过不代表可达。

**为什么**：这是 G1 的直接教训。压缩能力全绿但没人调用它。

**检查方式**：回答三个问题——
1. 用户从哪个入口触发这个能力？（CLI 命令？构造参数？配置项？）
2. 默认值是开启还是关闭？如果默认关闭，文档里怎么开启？
3. 有没有一个检查项验证"从这个入口进入后，能力确实被调用"？

**反例**：只有测试构造 `new SlidingWindowCompactor(...)`，生产代码从不构造它。

### 门 4：反证有效

**要求**：至少有一个检查项，在**故意破坏修复**后会失败。

**为什么**：
- 全绿的测试可能什么都没测（M1 里"跨 ALC 事件同一性"测试根本没有事件）
- 反证失败本身会暴露测试盲区（M1 里用量检查只测解码器不测发送端）

**做法**：改坏实现 → 重建 → 运行 → 确认目标检查失败 → 恢复 → 确认再次通过。

**注意**：`spike` 不在 solution 里，全量构建**不会**重建它。反证前必须单独构建
`spike`，否则跑的是旧 DLL——本项目因此白费过至少四次排查。

### 门 5：诚实记录

**要求**：`status.md` 里每一项都附证据位置（测试名、探针输出、提交哈希）。
未运行、失败、未覆盖的检查必须如实写出来。

**为什么**：文档勾选不替代测试结果。"已实现"这三个字如果可以为真，
那"已完成"就没有意义。

**具体做法**：
- 勾选时写清**什么验证了它**，不是写"已实现"
- 明确列出"未实现"与"明确保留的近似"
- 记录不准确时**改记录**，不要让记录慢慢失真

**反例**：G1 的 `status.md` 写"未实现真实模型摘要调用"，
但实际情况是"整条链路没接入"——记录不准确比功能缺失更危险。

### 门 6：文档同步

**要求**：改动影响到文档时，**同一提交**内更新。不允许"稍后补文档"。

**为什么**：M1 结束时发现 `design.md` 说"不能超预算继续请求"，
而实现是"预算不足则继续并上报"——表述冲突放了很久没人发现。

**需要检查的清单**：
- [ ] `architecture.md`：契约变了？新增了行为？
- [ ] `design.md`：决策变了？
- [ ] `status.md`：验收状态、证据位置、进度日志
- [ ] `plan.md`：缺口台账、顺序
- [ ] `README.md` / `README.en.md`：能力清单、环境变量
- [ ] `docs/README.md`：新增文档要进索引
- [ ] `journey/`：过程中有值得复盘的判断错误

## 三、红线（触发即停止，必须重新讨论）

这几条比门更硬。触犯任何一条，说明方向已经偏了，不是"这次做得不够好"。

| 红线 | 说明 |
|---|---|
| **宣称未验证的能力** | 文档写"支持 X"，但 X 没有真实运行过 |
| **静默降级** | 失败时不报告、不停止，假装成功 |
| **测试全绿作为验收依据** | 只有测试，没有生产路径证据 |
| **降低门槛以赶进度** | "这次先不验证，下次补" |
| **在可信插件模型下宣称沙箱** | 把审批当安全边界 |
| **自动重放不安全副作用** | `OutcomeUnknown` 时按"未执行"继续 |
| **用兜底逻辑掩盖主路径失效** | 主路径从未命中，靠 catch-all 让功能"看起来正常" |

最后一条值得单独说明：`finish_reason` 读错字段时，功能一直是好的——
靠流结束时的兜底下发。这比直接失败更危险，因为没有任何信号。

## 四、不同规模交付的门裁剪

不是所有改动都需要六道门全开。按规模裁剪，但**红线永远适用**。

| 规模 | 需要的门 |
|---|---|
| 文档/注释 | 门 6 |
| 重命名/纯重构 | 门 4（行为不变的反证）+ 门 6 |
| 缺陷修复 | 全部六道 |
| 新能力 | 全部六道 + 在 `plan.md` 登记对应哪条性质 |
| 里程碑关闭 | 全部六道 + 用 [goal.md](goal.md) §4 的整体判定复核 |

---

## 五、里程碑关闭时的附加要求

里程碑关闭 = 声称"这一层做完了"，因此门槛更高：

1. **逐项复核** `status.md` 的验收项，每项都要有可运行的证据，不是描述。
2. **用 `goal.md` §4 复核**：这个里程碑声称推进的性质，判定方式是否成立。
3. **独立复审**：由不携带本轮上下文的方式重新检查（M0 与 M1 都做过，
   每一轮都发现了问题，包括已被勾选的项）。
4. **诚实报告未覆盖项**：哪些验收项还没有验证、为什么、什么时候补。
5. **更新 `goal.md` §6** 的差距表。

## 六、这些门本身的维护

门不是一次性写好的。它们应该随着被绕过而变严：

- 出现一个新的"测试全绿但实际有问题"的案例 → 考虑加门或加严现有门
- 某道门在实践中证明无效（例如总是形式化通过）→ 改写它，而不是默默跳过

**门 3 的半自动检查已落地**：`spike/Dougong.Agent.Comparison/ReachabilityChecks.cs`
（`-- reachability`）用反射验证关键能力是否出现在生产类型的公开面上——
压缩器是否在 `LoopAgentRuntime` 构造参数里、dispatcher 是否接受 store、
用量装饰器能否包装任意 `IChatClient`、shell 是否实现 `IAgentTool`。

**它仍不完备**：能发现"完全没接进去"，发现不了"接进去了但走不到"（例如参数存在
但代码路径不触发）。因此门 3 的人工复核不可省。2026-10-24 用反向实验验证过它有效：
把构造参数改回 `object?` 后，检查精确报出"不接受 IContextCompactor"。

**这次反向实验还复查到一个教训**：第一次做反证时构建失败了（4 个 error），
却仍跑了旧的 DLL，得到"ALL PASS"的假结论。反证的第一步永远是**确认构建成功**——
这正是门 4 里写的那条注意事项。

**2026-10-24 又踩了两次同样的坑**（做 annotations 反证与 token 估算反证时），
说明"写下来的纪律"不等于"遵守了纪律"。因此已把它固化成脚本：
`scripts/all-checks.sh` **先单独重建 spike，再跑全部套件**。
spike 不在 solution 里，`dotnet build Dougong.slnx` 不会重建它——
这是该坑反复出现的唯一原因。凡是做反证，用这个脚本，不要手敲命令。

## 七、一份自检清单（贴在实际交付时用）

```text
[ ] 门 1  改动前有失败证据；改动后同一探针通过
[ ] 门 2  与外部系统交互的行为对照真实行为验证过，结论写在注释里
[ ] 门 3  用户从哪个入口触达？默认开关？有检查项验证触达吗？
[ ] 门 4  至少一个检查项在故意破坏后会失败（反证前已重建）
[ ] 门 5  status.md 每项附证据；未覆盖项如实写出
[ ] 门 6  关联文档同一提交内更新（含中英文 README、索引、缺口台账）
[ ] 红线  没有宣称未验证的能力 / 静默降级 / 降低门槛
```
