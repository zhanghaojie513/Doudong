# Dougong 未来迭代方向

> **定位**：本文件回答"M3 完成、产品可用之后，按什么顺序迭代、每个迭代做到什么程度算完成"。
> **与 [frontier-roadmap.md](frontier-roadmap.md) 的分工**：那份是外部事实调查（别人做到了什么、标准走到哪），这份是内部排序与切分（我们先做什么、放弃什么、何时转向）。
> **状态**：2026-10-23 编制。迭代顺序与退出条件是设计判断，不是交付承诺；所有条目均未实施。
> **前提**：M0–M3 的当前设计完成并通过验收。M3 之前不启动这里的内容。

---

## 1. 排序原则

1. **先能被别人用，再做平台。** 没有外部使用者的"平台"只是自娱。分发、诊断、文档先于新能力。
2. **标准优先，私有只补缺口。** ACP、MCP、Agent Skills 已定义的语义不自研；私有层只保留标准不管的部分。
3. **治理先于自动化。** 来源、版本、作用域、审批、撤销要先于"自动进化"；否则自动化只会放大不可控。
4. **可度量先于叙事。** 任何"变好了"必须能在独立任务集上复现，否则不进版本说明。
5. **单人可完成。** 每个迭代必须有明确的"可以不做"边界，避免无限扩张。

---

## 2. 迭代总览

| 迭代 | 主题 | 一句话目标 | 退出条件（摘要） |
|---|---|---|---|
| **I0** | 稳定化与发布 | 外部开发者能独立装上并用起来 | 陌生人仅凭文档完成安装→配置→跑通→写插件 |
| **I1** | 可嵌入运行时 | 从"一个 CLI"变成"能被 .NET 服务嵌入的库" | 一个真实 .NET 服务在生产形态嵌入并完成带审批任务 |
| **I2** | 执行边界 | 让改文件、跑命令在真实项目中可控 | 本地与容器后端行为一致，网络受限场景可验证 |
| **I3** | 知识资产化 | Skills/Memory 变成可治理资产 | 能回答"从哪来、谁批准、影响过什么、如何撤销" |
| **I4** | 可度量进化 | 把"自我提升"变成可复现实验 | 独立留出集上不劣于基线，失败案例可解释 |
| **I5** | 互操作 | 成为可被编排的节点，而非编排平台 | 在 MAF workflow 中作为子 agent 正常运行且语义不丢失 |
| **I6** | 产品面扩张 | 桌面为主产品、团队特性 | 仅在 I0–I3 有稳定外部用户后启动 |

必做：**I0、I1、I3**。差异化投资：**I2、I4**。观察后决策：**I5、I6**。

---

## 3. 各迭代定义

### I0 稳定化与发布

**目标**：把 M3 的能力变成别人能用的产品。

**交付**

- 安装与升级：`dotnet tool`、单文件发布、版本自检、配置迁移与回滚。
- 诊断：启动自检、分级日志、可复现信息包（版本、配置摘要、最近失败）。
- 文档：插件作者指南、嵌入指南、故障排查、最小可运行示例。
- 兼容策略：语义化版本、弃用窗口、实验性标记的明确边界。
- 分发：ACP Registry 上架，声明支持的方法与能力版本。
- 性能基线：大会话、长会话、并发会话的实测数字，写进文档而非宣称。

**不做**：新 agent 能力、新协议、新存储后端。

**退出条件**：一位未参与开发的人，在干净 Windows 与 Linux 环境各完成一次"安装→配置模型→完成一个真实任务→写一个工具插件"，全程无需提问。失败可定位到具体组件。

---

### I1 可嵌入运行时

**目标**：让 Dougong 成为 .NET 应用里的一个组件，而不是必须单独跑的进程。

**交付**

- 通用宿主抽象：由宿主提供模型、存储、审批、工具、日志，内核不抢控制权。
- `Dougong.Hosting.AspNetCore`：后台任务触发、SSE/WebSocket 推送、与现有 DI/配置/日志集成。
- `Dougong.Hosting.Worker`：队列/定时触发的无头运行。
- 多会话并发、配额、取消、优雅停机。
- 宿主级可观测：遵循 OpenTelemetry 语义约定，成本与延迟可聚合。
- 明确"库模式"与"进程模式"两种集成路径，以及各自的保证与限制。

**不做**：自建 agent 网关、自建任务队列、自建鉴权。

**退出条件**：一个真实 .NET 服务在不改变部署模型的前提下嵌入 Dougong，完成一次带审批与工具调用的任务；任务失败可定位到具体组件；优雅停机不丢已提交状态。

---

### I2 执行边界

**目标**：让"能改文件、能跑命令"在真实项目中可控，同时不承诺做不到的隔离。

**交付**

- 执行后端抽象：本地 → 容器 → SSH/远程，按需实现。
- 工作区策略：读写范围、网络允许列表、越界需显式批准。
- 每个后端**声明自己的保证级别**（进程约束、文件系统、网络），文档并列展示，不混用"沙箱"一词。
- 失败与逃逸路径的检测、告警与诊断。
- Windows 路径：优先容器/WSL2；原生 Windows 后端作为实验特性，单独标注成熟度。

**不做**：通用 OS 沙箱、跨平台统一隔离语义、安全认证。

**退出条件**：同一工具在本地与容器后端行为一致（除明确声明的差异）；网络受限场景有可验证结果；后端能力差异在文档中一目了然。

---

### I3 知识资产化

**目标**：让 Skills 与 Memory 从"提示词片段"变成可管理、可审计的资产。

**交付**

- 兼容 [agentskills.io](https://agentskills.io/specification) 格式，可导入导出。
- 每条记忆/技能记录：来源（任务与证据）、作用域（用户/项目/组织）、版本、内容哈希、审批记录、撤销状态。
- 启用与执行分离：技能中的脚本永远走统一工具管线。
- 撤销语义：影响新 turn，明确不影响已发生副作用；活动 turn 的暂停/重建规则。
- 审计查询：某条规则从哪来、谁批准、影响过哪些会话。
- 组织策略：哪些类别可自动启用，哪些必须人工批准；配置本身不可被进化产物修改。
- 隐私：本地存储与模型处理位置分别声明，两条外发数据流可独立关闭。

**不做**：技能市场、跨组织共享协议、自动放权。

**退出条件**：能在一次审计中完整回答来源、批准者、影响范围与撤销方式；在留出任务上启用前后无未解释的安全/隐私违规。

---

### I4 可度量进化

**目标**：把"越用越贴合"从叙事变成可复现的实验结果。

**交付**

- 基准适配层：同一引擎可跑 SWE-bench、Terminal-Bench 与自建 .NET 任务集。
- 自建任务集：贴近真实 .NET 项目（MSBuild、NuGet、SQL Server、Azure SDK、企业内网工具），公开任务描述、评分方式与失败案例。
- 评测集构建：从会话日志提取，但**与生成材料严格分离**；按项目/时间划分训练与留出。
- 离线优化：先作用于技能文本，再考虑提示与工具描述；参照 GEPA 类方法，不重造优化器。
- 门禁：测试通过、体积限制、语义保持、成本上限、安全与隐私检查、人工审查。
- 结果公开：版本、样本量、指标、失败案例、成本。

**不做**：在线自动改写生产会话、自动提交代码、无人工审查的自我修改。

**退出条件**：一次优化在独立留出集上可复现地不劣于基线，且每个退化案例都能解释；成本与延迟在可接受范围。

---

### I5 互操作

**目标**：不造编排平台，成为可被编排的节点。

**交付**

- MAF 适配：把 Dougong 会话暴露为 `AIAgent`，进入其 workflow。
- MCP Tasks：长工具与审批等待复用该扩展，减少自研状态机。
- A2A 等按实际采用度评估，不提前实现。
- 边界声明：编排、托管、企业 agent 服务交给 MAF/Azure，Dougong 提供引擎与治理。

**退出条件**：在 MAF workflow 中作为子 agent 正常运行；取消、错误、审批语义在跨框架调用中不丢失。

---

### I6 产品面扩张（决策点，不是默认路线）

**可选方向**

- Dougong Desktop 成为主产品，CLI 退为自动化入口。
- 远程/无头托管：服务器常驻引擎，桌面/移动连接。
- 团队特性：共享技能库、统一审批策略、审计报表。

**启动条件**：I0–I3 有稳定外部用户；出现明确的付费或组织采用信号。否则容易做成半成品。

**注意**：团队与企业特性可能改变开源定位，需单独决策，不在本文件预设结论。

---

## 4. 依赖与顺序

```text
I0 ──▶ I1 ──▶ I2
 │      │
 │      └────▶ I3 ──▶ I4
 │                    │
 └────────────────────┴──▶ I5 ──▶ I6（按信号）
```

- I0 是其余全部的前置。
- I1 与 I3 可并行，但 I3 的审计查询需要 I1 的宿主观测能力。
- I4 依赖 I3 的版本与来源记录，否则评测无法定位到具体变体。
- I5 可在 I2–I4 任一阶段之后启动，取决于外部框架采用度。
- I6 不设默认启动时间。

---

## 5. 触发式工作（不占固定迭代）

这些不由排期驱动，而由外部信号触发；触发后作为当前迭代的插入项处理。

| 信号 | 动作 | 判断依据 |
|---|---|---|
| ACP v2 结束 draft | 桌面内部会话语义收敛到 `session/resume` + `replayFrom`，删减私有扩展 | 标准稳定、SDK 支持 |
| MCP Tasks 被主流客户端支持 | 长工具与审批等待改用 Tasks 语义 | 客户端矩阵与 SDK 支持 |
| Skills over MCP 定稿 | 技能可从 MCP 发现，本地目录变为一种来源 | 工作组产出 |
| MAF 补上来源/审批/撤销治理 | 重新评估 I3 的差异化；必要时改为适配而非竞争 | 官方发布说明 |
| 公共基准饱和或与真实 .NET 场景偏离 | 加大自建任务集权重 | 榜单区分度 |
| Windows 原生隔离方案成熟 | 评估作为 I2 后端，而非替代容器 | 平台能力与稳定性 |
| 模型能力显著变化（如更长上下文、内置工具调度） | 重新评估压缩、工具粒度、循环所有权 | 实测而非宣称 |

---

## 6. 每个迭代的统一验收模板

任何迭代声明完成前，五项都要有证据，缺一项即视为未完成：

1. **功能**：正常路径在文档所列环境跑通，有可复现命令。
2. **故障**：列出该迭代相关的失败模式，逐项有测试或明确标注未覆盖。
3. **兼容**：协议版本、包版本、平台差异明确记录。
4. **文档**：外部用户可独立完成，不需要作者解释。
5. **成本与性能**：给出实测数字（token、延迟、内存、磁盘），不接受"很快""很省"。

---

## 7. 明确不做或长期推迟

- 通用 OS 沙箱与安全认证。
- LLM provider 矩阵。
- 多 agent 编排平台。
- 自建技能格式。
- 插件市场与交易基建。
- 与 dsh 插件数量对标。
- 默认开启的自动自我修改。
- 跨平台统一的终端屏幕状态恢复。

---

## 8. 资源建议

- 单人节奏下，**I0 与 I1 必须先做完**，否则后续迭代缺少真实反馈。
- **I3 是长期差异化的核心**，即使 I2/I4 延后也应保留。
- **I2、I4 是投资项**：做得好形成壁垒，做不好会拖慢主线，需设硬性时间盒。
- **I5、I6 不主动推进**，等外部信号；提前投入大概率浪费。

不给具体月数：每个迭代以退出条件为准，按实际投入速度推进。任何阶段都可以停下来发布，而不是必须走完全部迭代。

---

## 9. 什么情况下修改本文件

- 外部标准发生实质变化（见 §5），导致某迭代的交付内容被替代。
- 出现真实用户反馈，证明某个"必做"其实没人需要，或某个"不做"其实是刚需。
- 单人产能与计划严重偏离，需要砍掉投资项而非降低质量门槛。
- 项目定位变化（例如从 SDK 优先转为产品优先），需重排 I5/I6。

修改时保留原判断与修改理由，不要静默覆盖，便于回看决策链。
