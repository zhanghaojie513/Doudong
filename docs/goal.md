# Dougong 的最终目的与达成判定

> **这份文档的作用**：它是整个项目的"验收总纲"。任何一片工作开始前，先问"这推动了
> 哪一条目标"；任何一片工作宣称完成后，用 §4 的判定标准检验。
> **它不是什么**：不是设计文档（[design.md](design.md)）、不是架构（[architecture.md](architecture.md)）、
> 不是排期（[plan.md](plan.md)）、不是台账（[status.md](status.md)）。
>
> 文档各司其职，任何一份都不单独构成"做完了"的依据：
>
> ```text
> goal.md      为什么做、什么算达成（本文）      ← 判定标准，最稳定
> plan.md      按什么顺序做、还差什么            ← 排期，随发现调整
> quality-gates.md  每一片必须过哪些门           ← 门槛，不随进度放宽
> architecture.md / design.md    怎么设计         ← 契约，代码注释引用
> status.md    实际做到哪一步（附证据）          ← 台账，只认实测
> journey/     过程中真实踩过什么                ← 复盘素材
> ```

---

## 一、最终目的（一句话）

**交付一个 .NET 原生的插件化 Agent Harness SDK：内核小而有完整生命周期，运行能力由插件组合而成，
宿主能安全地装卸、重启、替换其中的任何一环，并且在崩溃、取消、超时与恶意/写错的插件面前
仍能给出可解释的结果。**

参照 dsh 的架构思想，不移植其代码。

---

## 二、这句话对应四条不可让渡的性质

下面四条是"最终目的"的可操作分解。它们不是并列的功能清单，而是**互相约束**的：
少任何一条，另三条都会失真。

### P1. 可组合（Composability）

运行能力（存储、审批器、工具、模型工厂、MCP 连接、REPL）能作为插件被组合进内核，
而不需要在宿主里永久缓存具体实现。

**不可让渡的部分**：只有现有扩展契约足够时，新能力才可以独立发布而无需修改内核。
需要修改内核才能接入的"可扩展"，不算可组合。

### P2. 有完整生命周期（Lifecycle Integrity）

注册、激活、停用、排空、清理、卸载各有明确语义与预算；任一阶段失败都不留
需要重启宿主才能清理的中间态（除非明确标记为隔离）。

**不可让渡的部分**：状态机里每个终态都可判定；没有"看起来成功"的路径。

### P3. 故障可解释（Explainable Failure）

崩溃、取消、超时、副作用结果未知时，系统能说清"哪些一定发生了、哪些一定没发生、
哪些不知道"，并且不自动重放不安全操作。

**不可让渡的部分**："不知道"必须能表达，不能与"没发生"混为一谈。

### P4. 真实可用（Actually Usable）

用真实 provider 跑真实任务时，协议层、工具管线与恢复语义都成立。

**不可让渡的部分**：只通过假模型验证的能力不算可用。假模型验证控制流，
真实 provider 验证协议与行为。

## 三、反目标（明确不做，做了就是跑偏）

写下来的目的不是限制野心，而是让"这算不算跑偏"可判定。

| 反目标 | 为什么不做 |
|---|---|
| 移植 Cordis 的完整响应式体系 | .NET 无对应物；"时空可组合"超出 harness 所需。只保留"依赖方随提供方重启"一条 |
| 追 dsh 的版本与实现细节 | 它高速演进；参照点冻结为其架构文档，追版本会永远落后 |
| 自研 provider 矩阵 / 重造 LLM 抽象 | 站在 `Microsoft.Extensions.AI` 上，自研范围压到"内核 + 运行时 + 协议壳" |
| 提供 OS 级沙箱 | 插件是可信进程内代码，审批约束的是**执行入口**，不是安全边界。宣称沙箱会是安全事故 |
| 做插件市场 / 桌面 UI / IDE 集成 | 由宿主项目承担（如 Dougong Desktop）；本仓库只交付 SDK + 参考 CLI |
| 把多 Agent 编排作为核心范围 | 不是当前生态位；强行并入会让内核契约变重 |
| 用"代码量小"作为正确性的理由 | 小内核的代价是概念密度高，不能靠省略验证来省事 |

## 四、达成判定（可执行标准）

每条性质都有**可观察的判定方式**，而不是"感觉做到了"。

### P1 可组合 — 判定方式

- [ ] 存在至少一种非内核提供的能力（存储、审批、工具、模型连接）能在**不修改内核代码**的
      前提下替换为另一种实现，且行为测试仍通过
- [ ] 依赖方向由测试守卫（`ArchitectureBoundaryTests`），任何 SDK 工程引用 UI/桌面技术栈即失败
- [ ] 内核零第三方依赖（除 `Microsoft.Extensions.*` 抽象）

**反例（出现即未达成）**：为了接入一种新存储而修改 `IAgentStore` 之外的任何代码。

### P2 有完整生命周期 — 判定方式

- [ ] 每个终态可判定：任一插件在任何时刻只有一个明确状态，且无"既像成功又像失败"的路径
- [ ] 每类资源（服务租约、事件订阅、清理回调、ALC）都有对应的释放证据
- [ ] 隔离（Quarantine）后的代次不可再激活、不可单独清理，且销毁时如实报错
- [ ] 对抗性探针覆盖：生命周期重入、并发启停、忽略取消、同步阻塞、重复销毁

**反例**：`CleanupFailed` 之后还能再激活；或排空超时后静默释放资源。

### P3 故障可解释 — 判定方式

- [ ] `OutcomeUnknown` 可表达，且恢复流程**不自动重放**外部副作用
- [ ] 恢复能重建"哪些调用被批准过"，"无记录"与"被拒绝"可区分
- [ ] 每个降级路径都发出带诊断的事件，而不是静默降级
- [ ] 取消与超时都结束整棵进程树/整个代次，不留并发重叠

**反例**：日志里有调用开始但无终态，恢复时按"未执行"处理。

### P4 真实可用 — 判定方式

- [ ] 至少 3 种协议（chat-completions / responses / anthropic messages）在真实端点上各跑通
- [ ] 真实编码任务：模型请求工具 → 审批 → 执行 → 结果回填 → 模型给出正确结论
- [ ] 长会话不因上下文超限失败（压缩生效）
- [ ] 会话 resume / branch 后能继续对话且历史完整

**反例**：只在假模型上验证过；或真实调用靠"兜底逻辑"掩盖主路径失效。

## 五、里程碑与这四条性质的关系

里程碑是**达成顺序**，不是目的本身。每个里程碑只推进其中一部分性质，
未覆盖的部分必须在 `status.md` 里如实留着未勾选。

| 里程碑 | 主要推进 | 明确不承诺 |
|---|---|---|
| M0 内核 | P2 完整生命周期 | P4（还没有真实 provider） |
| M1 入口与执行契约 | P3 故障可解释、P4 真实可用 | P1 的部分（插件生态还未成型） |
| M2 协议与集成 | P4 扩展到 MCP/ACP | P1（工具桥接不等于生态） |
| M3 生态与稳定 | P1 可组合（第三方插件、API 稳定） | 反目标清单里的任何一项 |

**里程碑完成 ≠ 最终目的达成。** 四条性质全部满足才算。

## 六、当前距最终目的的差距（2026-10-24）

| 性质 | 当前状态 | 主要缺口 |
|---|---|---|
| P1 可组合 | **部分** | 内核生命周期扎实、依赖方向有守卫；但插件生态未成型（M3），存储/审批的可替换性没有专门的验收测试 |
| P2 完整生命周期 | **基本达成** | 157 项测试 + 20 项对抗探针；剩余：断电级持久化只声明进程崩溃级 |
| P3 故障可解释 | **基本达成** | 四个提交屏障 + 审批记录 + 未知结果对账；剩余：工具幂等键（无法按契约核实未知结果） |
| P4 真实可用 | **部分** | 3 协议 + 真实编码任务 + 压缩 + 恢复都验证过；缺口在 MCP/ACP 尚未接入，工具箱只有文件读写与 shell |

**判断**：P2/P3 已接近可宣称；P1/P4 需要 M2/M3。按 `plan.md` 的顺序推进。

## 七、这份文档怎么用

- **开新片之前**：在 `plan.md` 里找到它对应哪条性质；找不到对应关系的，问"它推进了什么"，
  答不上来就是跑偏。
- **宣称完成之前**：用 §4 的判定方式自检，而不是用测试数量。
- **发现新缺口时**：登记到 `plan.md` 的缺口台账，并标注它影响哪条性质。
- **出现分歧时**：本文件的四条性质与反目标是仲裁依据；`architecture.md` 的技术选择可以改，
  但这四条不让渡。

**这份文档本身也需要被挑战**：如果某条性质在实践中证明不成立（例如 P1 的可组合性
在 .NET 的 ALC 模型下根本做不到），应修改本文并说明理由，而不是让实现悄悄绕开它。
