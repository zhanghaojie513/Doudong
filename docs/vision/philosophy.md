# Dougong 设计理念

> 本文回答“为什么这样设计”。技术契约见 [architecture.md](../architecture.md)，总体决策与里程碑见 [design.md](../design.md)，实际进度见 [status.md](../status.md)。2026-10-23 技术评审修订；下述内容是设计目标，不是已实现能力清单。

## 1. 名字与定位

斗拱以标准构件连接、分担载荷，作为 Dougong 插件组合的隐喻。Dougong 的目标是 .NET 原生 Agent Harness SDK：小内核承载运行组件，CLI 提供参考宿主，Dougong Desktop 提供独立桌面产品。

“一切皆插件”约束引擎的可扩展运行能力，不表示操作系统、启动器、UI、IPC 和所有基础库都必须实现为插件。内核负责生命周期、依赖满足、服务连接、事件和加载；承托正确性不能为了代码量小而省略。

## 2. 七条理念

### 2.1 用插件组合运行能力

Agent 运行实现、存储、审批器、工具、模型工厂、MCP 连接和 REPL 可以作为内核承载的组件。默认产品通过组合根装配它们，而不是在宿主中永久缓存具体实现。

重点是能力可替换：存储或审批等必需能力缺失时暂停工作，提供方恢复后重新评估；不是缺了什么都继续运行。只有现有扩展契约足够时，新能力才可以独立发布而无需修改内核。目录扫描属于发现步骤，依赖准备、兼容检查、信任确认、激活与卸载仍各有条件。

这一设计可称“构成引擎的构件”，但不据此断言其他 Agent 产品都只能添加附件。具体比较应针对版本、公开契约和实测行为。

### 2.2 小内核必须有完整生命周期

内核不实现模型推理或业务工具；它负责注册事务、依赖图、调用租约、排空、清理、状态与兼容性。服务新增、替换、移除都重新评估需求；必需需求不满足则进入 `Blocked`。

停止、重新激活和程序集卸载分别建模。ALC 提供依赖解析隔离与协作式卸载，不提供强制中止或安全边界；可信插件的清理失败应明确诊断，不能伪装为成功卸载。参照 dsh 的组合思想，不移植 Cordis 的完整响应式体系。

### 2.3 优先采用基础件，再验证组合语义

拟采用 M.E.AI 作为模型抽象，官方 MCP C# SDK 作为协议基础，Microsoft.Extensions 作为日志/配置等抽象，OpenTelemetry 作为可观测出口。当前骨架尚未接入产品外部包，这些是选型，不是已经验证的依赖。

MAF 的 HarnessAgent、中间件、历史与审批能力可本地使用；是否复用为运行实现，由同一提交、审批、取消和生命周期反例集比较决定。保持抽象与明确边界，不用“必须自研”或“框架已有”替代实验。具体版本在还原和编译后固定。

### 2.4 借思想，独立实现

dsh 是架构参照，不是逐提交追踪或行为兼容基准；不移植其 TS/Cordis 实现。Hermes、TKCode 等提供特定机制的参考，采用前要核实来源和边界，不能以其他项目存在某能力证明 Dougong 已成立。

Skills 是有来源和版本的内容，加载与进化机制由插件承载；技能不能另建执行通道。自动复盘先生成候选，经策略、评测和审核后才启用，持续改善需要实测。

### 2.5 协议与进程边界明确

外部 ACP 客户端通过 CLI 的标准 stdio 入口驱动引擎；桌面内部通过可重连命名管道与附着/快照扩展连接 AgentHost，不能假设标准 ACP 自带存活重连。

Desktop UI 不引用 `Dougong.*`，JIT AgentHost 直接内嵌 SDK，PtyHost 管理终端资源。CLI 是另一种独立宿主；两者复用 SDK，不叠加 CLI 包装进程。UI NativeAOT 是发布目标，实际依赖兼容性仍需发布验证。

存活重连与引擎崩溃恢复分别验收。UI 关闭时引擎可存活；引擎重启只恢复已提交记录，不能接管原内存调用或假装恢复旧 PTY。详见 architecture.md §6。

### 2.6 权限声明与执行校验配合

工具声明参数 schema、复合权限和资源计划，统一 dispatcher 负责校验、审批、执行前重查和终态记录。自描述减少中央权限表遗漏风险，但不证明声明真实；宿主保留逐工具覆盖，未知权限不自动批准。

审批绑定调用、工具版本/激活代次、参数、工作区和授权范围；工具替换或参数变化使旧许可失效。默认串行，已审查的工具再启用资源级并发。结果按序回填不代表副作用安全。

第一版可信进程内插件拥有宿主权限；ALC、工作区约定和审批不是 OS 沙箱。子进程可改善故障隔离，同一 OS 权限下也不等于恶意代码隔离。

### 2.7 已提交日志是真相源

会话使用 append-only 日志记录可恢复状态。副作用之前显式等待存储提交，持久化状态通知在提交后发布；订阅顺序不提供屏障。流式暂存文字可实时展示，但不包含在崩溃恢复保证中。

副作用已发生、结果尚未提交的窗口需要标记未知并核实，日志不能天然实现 exactly-once。杀进程与断电持久性分别验证。分支从已提交一致切面创建；隐私材料支持受控删除，append-only 不等于敏感数据永远不可清除。

## 3. 范围与反目标

SDK 仓库不实现桌面 UI/IDE，Dougong Desktop 是产品族中的独立宿主。当前不自研 provider 矩阵、不移植完整 Cordis、不建设插件市场、不做 OS 级沙箱，也不把多 Agent 编排作为核心范围。

NuGet 负责包分发，不自动完成插件发现、安装、依赖准备或可信激活。后续扩展以实际需求和验证成本决定，不能借类比扩大承诺。

## 4. 成功标准

- **技术**：M0–M3 的正向与故障验收通过，真实编码任务可完成，接口、恢复、审批和插件作者体验都有可复现证据。测试通过只证明其覆盖条件，不能承诺所有故障都已排除。
- **自用产品**：在持续维护模型连接器、运行环境和依赖的条件下，为 Dougong Desktop 和个人 CLI 提供可用引擎；不承诺“终身无需维护”。
- **生态**：发布后观察第三方插件、独立宿主与实际用户采用情况。它是待验证结果，不是由架构决定的必然成功。

Obsidian、VS Code 或 Serilog 只能帮助说明组合、分发或底座角色；Dougong 的身份仍是 Agent Harness SDK 与配套产品，具体能力以契约、实现和测试为准。
